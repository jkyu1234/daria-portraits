# Daria 魔法画像 — 产品需求与架构说明书

> 本文档 = 用户功能说明书 + 技术架构设计。
> 阅读本文档后，你可以完整理解：这个软件做什么、怎么用、以及它是如何运作的。

## 一、产品概述

### 1.1 产品定义

**Daria 魔法画像**是一个面向 Daria 动画粉丝的 AI 角色互动平台。核心体验是：用户与 Daria Morgendorffer 进行自然语言对话，系统实时评估互动质量并反馈"好感度"，同时提供数据看板、成就系统、以及自动推送的 Daria 社交媒体内容。

### 1.2 产品形态

| 维度 | 说明 |
|------|------|
| 类型 | 网页应用 (Web Application) |
| 渲染方式 | 客户端渲染 (CSR) — 页面在浏览器中动态生成 |
| 数据存储 | 云端数据库，用户数据不存储在用户本地电脑 |
| AI 引擎 | 接入第三方 AI 编排平台，通过 API 调用 |
| 部署方式 | 前端静态托管 + 后端云服务 (BaaS) |
| 访问方式 | 浏览器打开链接即可，无需安装 |

### 1.3 系统参与者

| 角色 | 说明 |
|------|------|
| 游客 | 无需注册，可直接聊天，数据仅保存在浏览器本地缓存中，关闭页面后一段时间清除 |
| 注册用户 | 邮箱或第三方账号登录，所有聊天记录、好感度、成就数据永久存储于云端 |
| 系统管理员 | 管理 Daria 社交媒体内容池、监控服务状态、审核异常行为 |
| AI 引擎 (Dify) | 提供角色扮演、情绪分析、好感度评估等核心智能服务 |
| 云数据库 (Supabase) | 提供用户认证、数据存储、实时推送等基础服务 |

## 三、用户系统

### 3.1 用户看到什么

打开网页即可聊天。注册后数据永久保存。用邮箱注册，或直接用 Google / GitHub 账号登录。

### 3.2 背后如何运作

**两种数据存储模式**：

| 模式 | 存储位置 | 生命周期 |
|------|----------|----------|
| 游客 | 浏览器 localStorage | 当前会话，关闭页面后最长保留 1 小时 |
| 注册用户 | Supabase 云数据库 | 永久保存，用户可随时回看 |

**认证流程**：
- 用户点击登录 → Supabase Auth 接管认证流程（支持邮箱密码、OAuth 第三方登录）
- 认证成功后，Supabase 返回一个会话令牌 (JWT Token)
- 前端拿到令牌后，后续所有操作自动带上身份标识
- 用户的数据查询自动限定为"只能看自己的数据"（行级安全策略）

**为什么游客可以试用但注册后功能更多？**
游客不需要后端存储任何东西，所有数据在浏览器本地。注册后数据从浏览器搬到云端数据库，这样才能实现跨设备同步、历史回看、数据统计等功能。

## 四、聊天系统（核心）

### 4.1 用户看到什么

页面分为三栏：

> **左侧** — Daria 的社交媒体。Daria 随手写下的想法、回忆、感悟。
>
> **中间** — 画像区。Daria 的画像会随着她当下的情绪而变化。
>
> **右侧** — 聊天区。你发消息，Daria 回复。顶部有历史对话列表（登录后可见）。

用户每发一句话，Daria 在几秒钟内回复。回复框上方出现浮动标签：`+3 ↑` 或 `-2 ↓`，告诉你这句话让好感度变化了多少。

### 4.2 背后如何运作

**一次完整的对话流程**（从用户点击"发送"到看到 Daria 回复，大约 3-8 秒）：

```
用户输入文字 "What do you think about high school?"
    │
    ▼
[浏览器] 构造请求
    │  包含：用户消息文本 + 会话ID（保持上下文连续性）
    │
    ▼
[Dify API] AI 工作流引擎
    │
    ├── [LLM 节点 ①] Daria 角色扮演
    │   输入：用户话语 + Daria 人设提示词 + 对话历史记忆
    │   输出：Daria 的回复文本
    │
    ├── [LLM 节点 ②] 情绪评分
    │   输入：用户话语
    │   输出：0-10 的整数 (score)
    │
    ├── [条件分支] 如果 score ≠ 5
    │   └── [LLM 节点 ③] 心理笔记生成
    │       输入：用户话语 + 话题上下文
    │       输出：一条讽刺风格的 Mental Note
    │
    ├── [LLM 节点 ④] 好感度变化评估
    │   输入：用户话语 + 对话历史
    │   输出：-5 ~ +5 的整数 (affection_delta)
    │
    └── [代码节点] 结果拼接
        输出：{ daria_chat, daria_score, daria_note, affection_delta }
    │
    ▼
[浏览器] 收到回复
    │
    ├── 显示 Daria 的聊天文本
    ├── 显示好感度变化浮动标签
    ├── 更新中间画像表情（根据 score）
    └── 如果有 Mental Note → 推送到左侧社交媒体栏
    │
    ▼
[Supabase] 保存消息记录（注册用户）
```

**好感度的计算公式**：

好感度 = 起始值（新用户默认 20 分）+ 所有历史对话中 `affection_delta` 的累加值

- 上限 100 分，下限 0 分
- 变化不是线性的：分数越低时涨得相对容易，越高时涨得越慢（类似游戏的升级曲线）
- 连续 7 天不聊天不会掉分——Daria 不 care 你什么时候来

**好感度等级的计算**：

| 分数区间 | 等级 |
|----------|------|
| 0-20 | "陌生人" |
| 21-40 | "勉强可以忍受" |
| 41-60 | "还算有趣" |
| 61-80 | "值得聊聊" |
| 81-100 | "仅次于 Jane" |

等级标签每次对话结束后自动重新计算。

**AI 模型说明**：

Daria 的角色扮演由大语言模型 (LLM) 驱动。系统提示词约 1500 字，包含：角色背景故事、人际关系、说话风格、世界观、输出格式约束。每次对话时，提示词 + 近 30 轮对话历史 + 用户最新消息一起发送给模型，模型据此生成 Daria 的回复。

这个提示词会在产品迭代中持续优化，以提升 Daria 的角色还原度。

## 五、画像系统

### 5.1 用户看到什么

中间画像不是静态图片，而是会根据 Daria 的情绪变化。

| 情绪 | 触发条件 | 画像表现 |
|------|----------|----------|
| 平静 | 情绪分 = 5 | 默认死鱼眼，微微不以为然 |
| 感兴趣 | 情绪分 6-7 | 眉毛微挑，眼镜反光 |
| 被逗乐 | 情绪分 8-9 | 嘴角出现一丝极微弱的弧度 |
| 惊喜 | 情绪分 = 10 | 罕见的几乎半笑 |
| 轻微厌烦 | 情绪分 3-4 | 眼珠微转，轻微白眼 |
| 生气 | 情绪分 1-2 | 明显白眼，交叉手臂 |
| 极度厌恶 | 情绪分 = 0 | 头埋在桌上 |

画像旁边有一个在线状态指示灯（[Daria 永远在线），以及一个数字气泡显示当前情绪分数。

### 5.2 背后如何运作

**表情切换逻辑**：
- Dify 返回的 `daria_score`（0-10 的整数）→ 前端根据分数查表 → 切换对应的表情图片
- 切换有 0.5 秒的渐变过渡动画，避免生硬跳变
- 如果某个分数的图片还未绘制，自动使用最近的已有图片（如 score=6 没有图，则使用 score=5 的图）

**图片素材结构**：

```
daria_expression/
├── score_0.png   (极度厌恶)
├── score_2.png   (生气)
├── score_4.png   (轻微厌烦)
├── score_5.png   (平静 - 默认)
├── score_6.png   (感兴趣)
├── score_8.png   (被逗乐)
└── score_10.png  (惊喜)
```

初期使用线下收集的 Daria 动画截图 + AI 图像工具辅助生成。后续可委托画师绘制统一风格的原创表情。

## 六、数据看板

### 6.1 用户看到什么

登录后，点击头像进入"我的 Daria 数据"。包含六个模块：

| 模块 | 内容 |
|------|------|
| 概览卡片 | 聊天总轮次、聊天天数、当前好感度、近 7 天趋势 |
| 专属词云 | 你的高频用词，越大 = 说得越多 |
| 热力图 | 日历格子，每天聊了多少，色块越深越多 |
| 好感度时间线 | 从注册到现在的等级变化，每次升降都有记录 |
| 话题分布 | 饼图展示你最常聊的话题类型 |
| 成就徽章 | 已解锁（亮色）和未解锁（灰色）的徽章墙 |

### 6.2 背后如何运作

**数据从哪里来？**

看板的所有数据都来自用户的聊天记录。每次对话结束后，系统在数据库中自动记录：
- 谁发的消息（用户 / Daria）
- 消息内容
- 当时的情绪分
- 好感度变化值
- 消息时间戳

这些原始数据在前端打开看板时被查询、聚合、计算，然后渲染为图表。

**为什么不是实时计算？**

当前版本数据量较小（单用户几千条消息级别），前端直接查询数据库并实时计算完全足够。如果未来用户量和数据量大幅增长，可以引入后端定时任务预计算统计结果，缓存后直接返回。

**词云如何生成？**

```
用户所有消息
    │
    ▼
提取文本 → 分词（按空格和标点切分）
    │
    ▼
去除停用词（the, a, is, I, to, of, and, it, that, in, for, you, me, my, was, are, be, have, do, just, like, so, not, but, this, they, what, when, can, about, all, if, or, as, at, no, your, we, he, she, her, his, an, will）
    │
    ▼
统计每个词的出现次数
    │
    ▼
按频率排序 → 取前 50 个词
    │
    ▼
前端词云组件渲染（频率 → 字号大小映射）
```

**成就徽章如何判定？**

每种成就是一个 IF 条件。例如：

- "Pizza 之友" → 扫描用户所有消息，`pizza` 出现次数 ≥ 20
- "马拉松选手" → 任意一个会话的消息数 ≥ 100
- "读心者" → 历史记录中 `score ≥ 8` 的次数 ≥ 5

每次对话结束后，系统自动扫描所有未解锁的成就条件，一旦满足即弹出通知、记录解锁时间。

## 七、社交媒体系统（左侧栏）

### 7.1 用户看到什么

左侧栏展示 Daria 的"社交媒体动态"，类似她的个人微博或 X 账户。包含四种内容卡片：

| 类型 | 触发条件 | 示例 |
|------|----------|------|
| 即时心理笔记 | 聊天中 score ≠ 5 时实时生成 | "Note to self: people will believe anything if you put it in a pie chart." |
| 动画回忆 | 与后台数据库有关，不定期推送 | "今天路过美术教室，看到有人在临摹 Mona Lisa，但把微笑改成了鬼脸。Jane 会 approve 的。" |
| 深夜感悟 | 每天 23:00 左右固定推送 | "凌晨 11 点，我在想：'早睡早起'是人类发明的最成功的 guilt trip 之一。" |
| 里程碑通知 | 好感度升级或成就解锁时即时推送 | 好感度升至 Lv.3，Daria 用讽刺语气"恭喜"你 |

用户可以给每条卡片点击反应：👍（赞）、😆（好笑）、🤔（值得思考）。

### 7.2 背后如何运作

**四种内容的生成方式**：

```
即时心理笔记：
  聊天 → Dify 返回 note → 前端直接渲染为卡片 → 同时存入数据库 → 所有用户可见

动画回忆：
  管理员维护一个"Daria 回忆内容池"（文本存储在数据库中）
  → 后端定时任务不定期从池中随机挑选一条
  → 标记为"已推送"
  → 所有在线用户通过实时订阅 (WebSocket) 收到推送
  → 新卡片出现在左侧栏顶部

深夜感悟：
  与动画回忆相同机制，但推送时间固定为每天 23:00
  内容池独立，专门存放 Daria 风格的深夜思考文本

里程碑通知：
  好感度升级或成就解锁事件触发
  → 系统即时生成一条 Daria 风格的点评
  → 仅推送给该用户本人
  → 其他用户不可见
```

**为什么用"不定期"而不是"固定间隔"？**

- 固定间隔（如每 2 小时推送一次）会显得机械，破坏 Daria 角色"随意、不经意"的感觉
- 不定期推送更像真人的社交媒体——有时候连发好几条，有时候一整天不说话
- 技术上用随机时间间隔（如 2 到 8 小时之间的随机值），模拟真实社交媒体的更新节奏

**实时推送如何实现？**

Supabase 提供"实时订阅"功能。简单理解：前端与数据库之间建立了一条持久连接，数据库中有新数据插入时，自动通知所有在线的浏览器。用户无需刷新页面就能看到新卡片。

**内容池的维护**：

Daria 的动画回忆和深夜感悟来自一个预先编写的内容池。内容池的条目由人工整理（从动画剧情、角色台词中提取），存储于数据库表中。每条内容包括：
- 正文（Daria 第一人称口吻的短文本）
- 分类（动画回忆 / 深夜感悟 / 系统通知）
- 来源（出自第几季第几集，便于追溯）
- 是否已推送过（避免重复推送）

内容池的初始规模约 50-100 条，后续可持续扩充。

## 九、安全与隐私

### 9.1 API 密钥保护

Dify 的访问密钥是最敏感的信息。在当前架构中：
- 密钥配置在前端环境变量中
- 生产环境下，建议通过后端代理转发 Dify 请求，避免密钥暴露在浏览器端

### 9.2 用户数据隔离

- 每个用户只能看到自己的聊天记录、自己的好感度数据、自己的成就
- 数据库的行级安全策略 (RLS) 强制执行此隔离
- 管理员可以看到全量数据用于运维，但无权查看用户的具体聊天内容

### 9.3 游客数据隐私

- 游客的聊天数据仅存在于浏览器本地，不上传到服务器
- 关闭浏览器或清除缓存后，游客数据永久消失
- 游客模式下 Dify 的对话 ID 不关联任何用户身份

### 9.4 社交媒体内容的来源

- Daria 的动画回忆内容来源于动画剧情片段
- 不包含任何真实用户的个人信息
- 用户对卡片点击的反应（👍/😆/🤔）是公开的，但评论功能暂不开放

## 十、实施优先级与依赖关系

### 10.1 各系统之间的依赖

```
用户系统 ─────────────────────────────┐
  │                                   │
  ▼                                   │
聊天系统 ──→ 好感度数据 ──→ 数据看板    │
  │                    │              │
  ├──→ 情绪分 ──→ 画像系统             │
  │                    │              │
  └──→ 笔记 ──→ 社交媒体栏             │
                       │              │
                       ▼              │
              成就徽章判定 ────────────┘
              (依赖聊天数据+好感度)
```

### 10.2 建议实施顺序

| 阶段 | 内容 | 依赖 |
|------|------|------|
| Phase 1 | 用户系统（Supabase Auth）| 无 |
| Phase 2 | 聊天系统升级（好感度 + 聊天历史持久化）| Phase 1 |

### A. Daria 角色提示词（概要）
